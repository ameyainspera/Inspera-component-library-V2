# Roles: how the primary user role changes design

> Reference file for `DESIGN.md` (Inspera Design System). Read it when you know the primary user role and are deciding density, wording, content, states or privacy. `DESIGN.md` wins if the two disagree.

## How the role changes design decisions

The team has confirmed the anonymity, moderation, Invigilator device and candidate rows. The rest is proposed and still needs validating.

| Decision | Author | Planner/admin | Invigilator | Grader/marker | Moderator | Test taker/candidate |
| --- | --- | --- | --- | --- | --- | --- |
| **Usage pattern** | Long creative sessions, repeated over weeks | Periodic, setup-heavy bursts before each exam period | Short, intense, live for the exam's duration | Long, repetitive sessions under a deadline | Focused review sessions after marking | Once per test, time-limited, high stakes |
| **Expertise** | Subject expert; some assessment design knowledge | Power user of the platform's settings | Varies; often not a platform expert | Subject expert; platform is a tool | Senior subject expert | Anyone; no platform training assumed |
| **Density** | Medium: editor space first, settings secondary | High: forms, tables, many options | Glanceable: big status signals, little text | High but focused: one response at a time with the rubric beside it | High: comparisons across markers and candidates | Minimal: one task in view, no clutter |
| **Typical screens** | Create/edit form, editor with preview | Create/edit form, settings, multi-step flow, list page | Overview/dashboard, list with live status | Detail page with side-by-side panels | List page plus detail/compare view | Dedicated test-player layout, not a library screen template |
| **Key components** | Form fields, Tabs, Accordion, Tag (metadata), Drawer (preview/details) | FormField, Select, DatePicker, Toggle, Table/DataGrid, Stepper, Drawer | Stat, Badge (status), DataGrid with live rows, Alert, Snackbar | NumberInput/Rating/RadioGroup for scores, Textarea (feedback), Pagination (next response) | Table/DataGrid, Badge, Drawer (compare), Dialog (resolve) | Large readable content, RadioGroup/Checkbox/Textarea for answers, Progress, an always-visible timer |
| **Primary action** | Save / Preview | Publish / Schedule / Run | Act on one candidate (add time, unlock) | Submit mark and go to next | Confirm or adjust a mark | Next question / Submit test |
| **Wording** | Assessment-design terms are fine | Product terms are fine (ATC, template, sitting), explained once | Plain, short, action-first ("3 candidates need help") | Marking terms (rubric, criterion, band) | Marking and quality terms (discrepancy, sample, appeal) | Plain, calm, no jargon, never alarming; follows the test's language |
| **Analytics and data insight** | Item statistics: difficulty, discrimination, how often an item has been used | Readiness and completion figures for setup and delivery | Live counts only (started, submitted, need help) | Own progress; score distribution for the questions they mark | Marker agreement, score distributions, discrepancies between markers, sample coverage | None during the test; results only if and when released |
| **Raw technical data** (JSON, API endpoints, internal IDs) | Hidden; IDs only where they're needed to reference items | Behind "Technical details", collapsed | Never | Never | Never, beyond the IDs needed to reference a script | Never |
| **Destructive and irreversible actions** | Confirm deletes; version history over confirmations | Confirm anything that affects many candidates, and show the count ("Affects 240 candidates") | Confirm actions on a live candidate; make them reversible where possible | Allow undo of the last mark; confirm only on final submission | Confirm overrides and record a reason | Confirm final submission once, clearly; no other blocking dialogs |
| **Feedback** | Autosave status; Snackbar on save | Inline validation; summary Alert before publish | Real-time status changes need to be noticed, using Badge and Alert as well as colour | Fast and quiet: progress count ("12 of 40 marked") | Show what changed and who changed it | Reassuring and constant: "Answer saved", time left; never a Snackbar that can be missed |
| **Privacy** | — | Sees candidate personal data; mask it in screenshots and demos | Sees candidate identity (needed to help) | **Depends on the test:** marking may be anonymous or named. Ask which. When anonymous, never show candidate identity anywhere, including in URLs, tooltips and exports | **Depends on the moderation setup.** Visibility of candidate identity, other markers' marks and comments, and whether the moderator sees the whole cohort or only sample scripts varies. Ask which | Sees only their own data |
| **Environment** | Desktop, large screen | Desktop | **Laptop or iPad**, in an exam hall or remotely, often while moving around. Design for touch and for the `md`–`lg` widths (768–1024px), in portrait and landscape. No hover-only actions, and targets at least 44px | Desktop, sometimes a second monitor | Desktop | Exam device: laptop, Chromebook or a locked browser; possibly unreliable network |
| **Accessibility emphasis** | Rich editor must be fully keyboard operable | Complex forms: labels, errors, focus order | Status must not rely on colour; must be readable at a glance and from a distance | Keyboard shortcuts for repetitive marking; low visual fatigue | Tables readable by screen reader; comparisons not colour-only | **Highest bar**: WCAG 2.2 AA minimum, screen reader, zoom/reflow, extra time and other accommodations, no time-based surprises |
| **States to design** | Draft, unsaved changes, preview, validation errors | Not configured, partly configured, scheduled, live (locked settings), no permission | Waiting to start, live, candidate needs help, disconnected, submitted | Not started, in progress, marked, flagged, locked by another marker | Agreement, discrepancy, appealed, resolved | Not started, in progress, saving/offline, time warning, submitted, time up |

## What this means for the library and the plane rule

- **Staff roles** (Author, Planner/admin, Invigilator, Grader/marker, Moderator) use this library and the full guide's screen templates as written.
- **Test taker/candidate** screens run in the test player, a separate surface with its own rules: a locked browser, an always-visible timer and answer autosave. Whether this library applies there **depends on the case**. Always ask for **screenshots of the current test player** as the starting point. Then apply the plane rule: same-plane additions match the screenshots, and a new plane uses the library only if the team confirms it is in scope for candidates. Anything that neither the screenshots nor the library cover is marked `DESIGN_SYSTEM_GAP`, never improvised.
- **Live roles** (Invigilator, and the candidate during a test) must never get a modal that blocks work without warning. Prefer inline status and Alerts over Dialogs.
